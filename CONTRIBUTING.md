# Contributing

Devcontainer features, published to `ghcr.io/kingofkalk/devcontainer-features/<id>`.

## Layout

- `src/<id>/devcontainer-feature.json`: metadata and options (`version` is managed by release-please)
- `src/<id>/install.sh`: runs as root at image build time
- `src/<id>/README.md`: hand-written docs (usage, every option, platforms, privacy, limitations)
- `test/<id>/test.sh`: test with default options
- `test/<id>/scenarios.json` + `test/<id>/<scenario>.sh`: option scenarios, one script per scenario name
- `.github/workflows/ci.yml`: lint, validation and tests
- `.github/workflows/release-please.yml`: release PRs, tags and GHCR publishing
- `release-please-config.json`, `.release-please-manifest.json`: one release-please package per feature

## Feature conventions

- One tool per feature. Users combine features in `devcontainer.json` instead of features bundling each other.
- Do not reference this collection's own features in `installsAfter`/`dependsOn`. The devcontainer CLI resolves them from GHCR, so tests fail until the referenced feature is published. Prefer runtime discovery (e.g. a binary on `PATH`) over install order.
- Option names are camelCase. Every feature with an upstream binary has `version`. A leading `v` is optional.
  - The default is pinned to a tested upstream release (`x.y.z`); `latest` stays a proposal. Reproducible builds, and CI does not break on new upstream releases.
  - `.github/workflows/pinned-versions.yml` proposes updates of the pin (see Dependencies). Add every new feature with an upstream binary to its matrix.
  - Upstream without checksums: pin the sha256 of known releases in the feature (e.g. `src/lightpanda/checksums.txt`) and add a bump hook that records them for new versions.
- Telemetry is always off by default. Expose a `telemetry` boolean (default `false`) if the tool has any.
- Download `latest` via `https://github.com/<owner>/<repo>/releases/latest/download/<asset>`, not the GitHub API (no rate limits).
- Verify checksums whenever upstream publishes them.
- Support Debian/Ubuntu (`apt-get`) and `x86_64`/`aarch64`. Fail with a clear `(!) <id>: ...` message otherwise.
  - Features that install no packages may support more distros (e.g. Alpine). Their scripts are POSIX `sh` and work with BusyBox; the feature README lists the supported platforms.
- Wrapper pattern: when an option must apply at runtime (env vars, default flags), install the real binary to `/usr/local/lib/<id>/` and generate a small `/bin/sh` wrapper at `/usr/local/bin/<binary>`.
  - `containerEnv` is static and cannot depend on options.
  - The wrapper `exec`s the real binary with `"$@"` unchanged.
  - Embed option values with single-quote escaping (`shell_quote`).
  - The devcontainer CLI writes option values unescaped into a sourced `KEY="value"` env file, so `"`, `$`, `` ` `` and `\` in string options are unsupported. Document this in the feature README.
  - User-provided env vars or flags win over option defaults.
  - Honor `<NAME>_REAL_BIN` so tests can swap in a stub.

## Adding a feature

1. Create `src/<id>/devcontainer-feature.json` with `"version": "1.0.0"`, `install.sh` (executable) and `README.md`.
2. Create `test/<id>/test.sh` and scenarios for each option.
3. Check that `.github/workflows/ci.yml` lists or detects the new feature.
4. Register it in `release-please-config.json` (copy an existing package entry, set `component`) and in `.release-please-manifest.json` with `"0.0.0"`.
   - The first release follows from the commits.
   - Use `"release-as": "1.0.0"` only if the feature should start at 1.0.0, and remove it after that release, otherwise every later release stays `1.0.0`.
5. Add a row to the feature table in `README.md`.

## Testing

### Locally

```bash
npm install -g @devcontainers/cli
devcontainer features test -f <id> -i debian:bookworm .               # default test on a base image
devcontainer features test -f <id> --skip-autogenerated .             # scenarios only
```

- Tests use `dev-container-features-test-lib` (`check "<label>" <command...>`, `reportResults`).
  - The library needs bash. Test scripts use `#!/bin/bash`; images without bash need a scenario Dockerfile that adds it.
- A folder `test/<id>/<scenario>/` is copied into the scenario's `.devcontainer/`, e.g. for `"build": {"dockerfile": "Dockerfile"}`.
- Checks that `features test` cannot express (expected build failures, rebuilds) live in `test/<id>/host/` as scripts run on the host (Docker and the devcontainer CLI). Entry point `test/<id>/host/run.sh`, which knows its own images and cases; the `host` job in `ci.yml` runs it for every changed feature that has it, once per architecture.
- Pure-shell unit tests (no Docker, no network) live in `test/<id>/unit/`, entry point `test/<id>/unit/run.sh`. The `unit` job in `ci.yml` runs them for every changed feature that has them.

### CI

- `.github/workflows/ci.yml` runs on every PR with these jobs:
  - `lint`: JSON syntax, shellcheck (all `*.sh`, severity `warning` and up, info and style notes are ignored), actionlint (all workflows, including shellcheck on `run:` blocks; runner labels in `.github/actionlint.yaml`)
  - `validate`
  - test matrix: feature x `debian:trixie`, `debian:bookworm`, `ubuntu:26.04`, `ubuntu:24.04` x amd64/arm64 on native runners, plus scenarios
  - `unit` and `host`: unit and host-side tests of changed features that have them
  - `test`: gate job that summarizes the results
- Only changed features are tested.
  - Changes outside `src/<id>/` and `test/<id>/` test all features, except docs (`docs/`, `*.md`) and release metadata (`.release-please-manifest.json`, `release-please-config.json`), which test none.
  - A release PR tests only its feature (through `src/<id>/CHANGELOG.md`).

## Workflow conventions

- `permissions: {}` at the top of each workflow, minimum permissions per job.
- Actions pinned by full version tag (`actions/checkout@v7.0.1`), not by commit SHA or major tag (`@v7`).
- Runners pinned explicitly (`ubuntu-26.04`, `ubuntu-26.04-arm`), never `*-latest`.

## Commits and pull requests

- Conventional commits, scoped by feature: `feat(<id>): ...`, `fix(<id>): ...`, `docs(<id>): ...`.
  - release-please derives each feature's version bump from commits touching `src/<id>/`.
  - `!` in the PR title (`feat(<id>)!: ...`) bumps the major version, which changes the `:<major>` reference users pin. A `BREAKING CHANGE:` footer in the PR body has no effect (squash commits have an empty body).
- Squash merge only. The PR title becomes the commit subject, so it must follow the same convention.

## Releases

- `.github/workflows/release-please.yml` opens one release PR per feature (`separate-pull-requests: true`).
- Merging a feature's release PR tags `<id>-vX.Y.Z`, creates a GitHub release and publishes the feature to GHCR.
- The workflows use only `GITHUB_TOKEN`, no secrets. Release PRs are authored by `github-actions[bot]`.
  - Release PRs get a normal `pull_request` CI run when they are opened or updated.
  - The first release PR may wait for "Approve and run workflows" (repo policy for first-time contributors, `github-actions[bot]` counts as one).
- Feature versions are independent of the upstream tool version.
- Repo setting "Allow GitHub Actions to create and approve pull requests" must stay enabled for release-please.

## Dependencies

- Dependabot updates workflow actions weekly (`chore(deps)`). Minor and patch updates auto-merge once the required checks pass.
- The Node and `@devcontainers/cli` versions and the shellcheck and actionlint images pinned in `ci.yml` are bumped by hand.
- Pinned upstream versions (a feature's `version` default, e.g. `openshell`): `.github/workflows/pinned-versions.yml` checks the upstream latest release every Monday and opens a PR `fix(<id>): update <Upstream> to <version>` (script `.github/scripts/bump-pinned-version.sh`).
  - New pinned feature: add `feature` and `upstream` (`owner/repo`) to the workflow's matrix.
  - The PR is created by `github-actions[bot]`, so CI needs one "Approve workflows to run" click.
  - Closing the PR skips that version; the next newer release gets a new PR.
  - Locally: `.github/scripts/bump-pinned-version.sh <id> <owner/repo> --dry-run`.
